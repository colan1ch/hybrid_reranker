## Сегодня-завтра (16–17 октября): решения и доступы

### Решить три вопроса — вместе, до первого запуска

От ответов зависят настройки в `config.toml`, а менять их потом значит начинать заново.

1. **Сколько вопросов.** Предлагаю `validation_size = 100`, `test_size = 200`: на 300 тестовых лимита впритык.
   Дорогая модель на 300 вопросах займёт около 3,6 дня лимита вместо 4,8.
2. **Откуда брать вопросы.** Предлагаю `sample_source = "beir_test"`: порог подбирается и проверяется на вопросах из одного набора.
   В исходном варианте проверочные вопросы легче тестовых, и порог может «не переехать».
3. **Что считаем успехом.** Записать числа заранее, например:
   - «каскад теряет не больше 0,02 nDCG@10 по сравнению с „всегда дорогая“ и вызывает её меньше чем в половине вопросов»;
   - «правило заметно лучше монетки».

Научные данные (SciFact) не берём: не успеваем. Упомянем как дальнейшую работу.

Готово, когда: ответы записаны в раздел 0 `RESULTS_PLAN.md`, `config.toml` поправлен.

## Запуски — Коля

### Шаг 1. Поиск и BERT (пт–сб, на видеокарте)

```bash
pip install -e ".[dev,plots]"
pytest -q                 # всё должно быть зелёным
rerank prepare
rerank retrieve           # несколько часов на видеокарте
rerank run --split validation --method dense
rerank run --split validation --method bert
rerank run --split test --method dense
rerank run --split test --method bert
rerank estimate           # покажет, сколько дней лимита нужно, по реальным текстам
```

После этого видеокарта не нужна. Папки `runs/main/` и `data/` переносим на машину, которая может работать несколько суток подряд.

### Шаг 2. Дорогая модель и ответы (вс–пт, без видеокарты)

**Важно:** все запуски с API делать **на одной машине** и не удалять `data/api.jsonl`.
В нём кэш ответов: каскады отправляют те же запросы и получают ответы бесплатно. Без кэша они потратят лимит заново.

Лимиты у дорогой модели (120B) и у генератора (20B) **отдельные**, поэтому их запускаем **одновременно в двух терминалах**.

**Терминал 1, дорогая модель:**
```bash
rerank run --split validation --method llm --allow-api   # ~1,2 дня
rerank tune                                              # без API
rerank gate                                              # без API
rerank run --split test --method llm --allow-api         # ~2,4 дня на 200 вопросов
```

**Терминал 2, генератор ответов** (можно начинать сразу после шага 1):
```bash
rerank run --split test --method bert --answers --allow-api
rerank run --split test --method dense --answers --allow-api
# когда терминал 1 закончит тест:
rerank run --split test --method all --answers --allow-api
```

- Флаг `--allow-api` означает: «я проверил, что тариф бесплатный и карты нет».
- Когда кончается суточный лимит, команда останавливается сама. Через несколько часов запускается **та же** команда, она продолжит с места остановки.
- Если `rerank gate` пишет, что мало примеров, где дорогая модель помогла, это тоже результат: записать долю и обсудить.
  Отчёт соберётся и без мини-модели.
- Проверку порядка текстов (`llm_input_order = "bert"`) делаем, только если останется лимит после 23-го. Иначе пишем как ограничение.

### Шаг 3. Таблицы и рисунок (пт 23, без API)

```bash
rerank evaluate --split test --method all --answers
rerank controls --split test
rerank resplit
rerank report --split test
```

Получаются `report/test/figure_2.pdf`, `table_1.tex`, `table_2.tex` и `controls/test.cases.csv` для разбора ошибок.

## Текст — Дима (параллельно с запусками)

Эти части не зависят от чисел, их надо закончить до 23-го.

1. **Шаблон** (сб 17). Скачать шаблон конференции и проверить, сколько места занимает пустой шаблон с заголовками.
2. **Введение** (сб–вс, около 0,5 страницы).
   - Задача: система отвечает на вопросы по Википедии.
   - Проблема: дорогая модель ранжирует лучше, но каждый вызов тратит лимит и время.
   - Наш вопрос и вклад: проверка с монеткой и оракулом. Новым методом не называем.
3. **Обзор литературы** (вс–пн, около 0,5 страницы). Список работ в `PLAN_ADDITIONS.md`:
   - Bacellar (вратарь, и правило «разрыв» как его базовый вариант);
   - ARDS, Genc и др., Dabod и др., BalanceRAG, AcuRank;
   - FrugalGPT, RankGPT, CoRank, Ni и др.;
   - каскадное ранжирование Wang, Lin, Metzler 2011.

   Главный абзац: чем мы отличаемся от Bacellar (сигнал от BERT, а не от поисковика; запасной порядок BERT; полный корпус; итоговые ответы и реальные токены).
4. **Метод и постановка эксперимента** (пн–чт, около 1 страницы).
   - Модели, данные, 20 кандидатов, правило порога, мини-модель, контроли.
   - Метрики: nDCG@10, «оба нужных текста в топ-5», EM, F1, токены, доля вызовов.
   - Две обязательные оговорки:
     - порог мини-модели подбирается по отложенным частям проверки, а применяется модель, обученная на всех проверочных вопросах;
     - оракул вызывает дорогую модель ровно столько раз, сколько правило, поэтому это не «вызов только там, где поможет».
5. **Рисунок 1** (чт). Вопрос → поиск (20 текстов) → BERT → ромб «разрыв ≤ порога?» → дорогая модель или порядок BERT → генератор ответа.
   Чёрно-белый, в одну колонку. Если не влезаем по объёму, убираем первым.
6. **Правила конференции** (до пт). Указание использования ИИ при подготовке работы, анонимность, язык, взнос.

## Если что-то пошло не так

| Проблема | Что делать |
|---|---|
| Groq требует карту | Ничего не запускать, сразу обсудить замену |
| К субботе нет видеокарты | Запускать поиск на процессоре немедленно (~3 суток) и урезать тест до 150 вопросов; сроки впритык |
| Запуски идут медленнее, чем ожидали | Решить вместе, не урезать ли тест до уже готовых вопросов (оставить в `test.jsonl` только их и пересчитать таблицы). Новых вызовов это не требует |
| Мини-модель не учится | Это результат: записать долю, обсудить; отчёт соберётся без неё |
| Правило не лучше монетки | Тоже результат: статья про то, почему простой сигнал не работает |
| Не влезаем в объём | Убрать рисунок 1, сжать обзор, детали в анонимный репозиторий |
