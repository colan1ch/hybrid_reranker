# План статьи: выборочное LLM-реранжирование в RAG

## Кратко

Проверить, может ли каскад **быстрый BERT-подобный реранкер → LLM только для неуверенных запросов** сохранить качество полного LLM-реранжирования, заметно сократив расход токенов.

Просто сравнить BM25, BERT и LLM уже недостаточно: LLM-реранжирование изучалось раньше. Сильнее будет сфокусироваться на том, **как распознавать запросы, которым действительно нужен LLM**, и измерить компромисс между качеством и затратами. [Исследование RankGPT](https://aclanthology.org/2023.emnlp-main.923/)

## Эксперимент

- **Бенчмарк:** BEIR HotpotQA. Это задача поиска документов для вопросов, требующих нескольких свидетельств; в наборе есть разметка релевантных документов и опорных фактов. [BEIR](https://arxiv.org/abs/2104.08663), [HotpotQA](https://arxiv.org/abs/1809.09600)
- **Базовый поиск:** один и тот же dense retriever `BAAI/bge-base-en-v1.5`; для каждого запроса сохранять top-20 кандидатов. У всех вариантов реранжирования должен быть один и тот же список кандидатов.
- **Сравнить четыре варианта:**
  1. Обычный RAG: взять первые пять результатов dense retrieval.
  2. Реранжировать top-20 моделью `BAAI/bge-reranker-base`, передать генератору первые пять.
  3. Реранжировать те же 20 документов GPT-OSS 120B на каждом запросе.
  4. Каскад: BERT-реранкер обрабатывает все запросы, а GPT-OSS запускается, когда BERT-реранкер не уверен в порядке первых результатов.
- **Правило вызова LLM:** основной сигнал — малый разрыв между оценками первого и второго документов у BERT-реранкера. Порог выбрать на validation-части, затем зафиксировать для теста. Низкую cosine similarity тоже проверить как отдельный вариант правила: сама по себе она может быть ненадёжна, а реранкер не найдёт документ, которого нет среди top-20.
- **RAG-ответы:** на одинаковом наборе запросов использовать один фиксированный генератор GPT-OSS 20B с одинаковым промптом и ограничением контекста. Проверять ответы по EM/F1 и измерять, попали ли опорные факты HotpotQA в выбранные фрагменты.
- **Размер выборки:** 100 запросов из validation для выбора порога и 300 запросов из test для сравнения; случайную выборку зафиксировать и сбалансировать по сложности запросов. Для оценки неопределённости посчитать парные bootstrap-интервалы.

## Метрики и гипотеза

Основная метрика поиска — **nDCG@10**. Дополнительно: Recall@20, MRR@10 и полнота опорных фактов в top-5. Для ответов — EM и token-level F1.

Для LLM сохранять фактические входные и выходные токены из ответов API. Отдельно показать токены на запрос и долю запросов, отправленных в LLM. Если приводить денежную оценку, рассчитать её по опубликованному тарифу отдельно от фактического расхода на бесплатном уровне.

**Гипотеза:** каскад удержит качество поиска близко к полному LLM-реранжированию, сократив расход токенов. Результат оценивать по измерениям; заранее не утверждать, что гипотеза подтвердится.

## Ограничения и привязка к конференции

Лучшее соответствие ICIICE — **трек 3.9: Generative AI in Engineering Design and Scientific Discovery**, если подать работу как исследование эффективного RAG для поиска научных свидетельств. Официальный срок подачи указан как **27 ноября 2026 года**, объём статьи — 4–6 страниц. [ICIICE 2027: темы и сроки](https://iciice.com/)

Для GPT-OSS 120B у Groq указаны бесплатные лимиты: до 1 000 запросов и 200 000 токенов в день для модели; квоты могут зависеть от аккаунта и меняться. План — использовать только бесплатный уровень, сохранять учёт токенов и остановить прогон при достижении квоты. Документация описывает оплату при переходе на Developer tier, но отдельно не гарантирует отсутствие запроса карты при регистрации: если бесплатный ключ нельзя получить без карты, этот сервис не использовать.
