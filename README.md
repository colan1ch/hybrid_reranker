# Выборочное LLM-реранжирование

Обвязка для эксперимента на BEIR HotpotQA: один dense-поиск top-20, несколько вариантов ранжирования (таблица ниже) и одинаковый генератор ответов. Полные эксперименты пока не проведены.

| Режим | Ранжирование |
| --- | --- |
| `dense` | Порядок `BAAI/bge-base-en-v1.5` |
| `bert` | Все top-20 через `BAAI/bge-reranker-base` |
| `llm` | Все top-20 через GPT-OSS 120B |
| `cascade_gap` | BERT; при малом разрыве top-1/top-2 вызывается GPT-OSS 120B |
| `cascade_cosine` | Отдельный вариант: вызов LLM при низкой максимальной cosine similarity |
| `cascade_gate` | Логистический gate на трёх числах BERT; сборка по сохранённым результатам без API |

Реранкер BERT возвращает сырые logits, без sigmoid. LLM получает кандидатов в исходном dense-порядке; этот же вызов используется в полном LLM-режиме и каскадах. Для проверки, не занижает ли это полный LLM, есть `llm_input_order = "bert"`: кандидаты передаются в порядке BERT. Это другая настройка, поэтому нужна отдельная `run_dir`; туда можно скопировать `candidates.jsonl`, файл вопросов и BERT-результаты нужного split (при желании урезав файл вопросов до подвыборки), затем выполнить `run --method llm`. Во всех режимах GPT-OSS 20B получает первые пять документов с одинаковым промптом и ограничением длины.

## Установка

Нужен Python 3.11 или новее.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e .
cp .env.example .env
```

В `.env` вписать `GROQ_API_KEY`. Он нужен для LLM-реранжирования и генерации ответов. Для подготовки данных, dense и BERT ключ не нужен.

Настройки находятся в `config.toml`. `device` и `batch_size` можно менять в любой момент (например, `cuda` или `mps`): они влияют только на скорость, и запуск продолжается в той же папке `run_dir`. Поиск `retrieve` лучше посчитать один раз на одном компьютере и передать `candidates.jsonl` второму: на CPU и GPU эмбеддинги чуть различаются, а `candidates.jsonl` должен быть общим. Любая другая настройка при изменении требует нового `run_dir`: настройки сохраняются рядом с результатами, смешивать результаты разных конфигураций команда не позволяет. Версии Python и библиотек сохраняются в `environment.json`.

Тесты (без сети и без обращений к API): `pip install -e ".[dev]"`, затем `pytest`.

## Запуск

```bash
rerank prepare
rerank retrieve

rerank run --split validation --method bert
rerank run --split validation --method llm --allow-api
rerank tune

rerank run --split test --method all --answers --allow-api
rerank evaluate --split test --method all --answers
```

Всё, что может обращаться к API (режимы `llm`, `cascade_*`, `all` и любой запуск с `--answers`), требует флага `--allow-api` (или переменной окружения `RERANK_ALLOW_API=1`). Флаг означает: «я проверил в консоли Groq, что аккаунт на бесплатном тарифе и к нему не привязана карта». Код сам тариф определить не может.

Если LLM вернула неполный ответ или список, который не является перестановкой, запрос повторяется один раз с другими параметрами. Если и повтор не удался, берётся порядок BERT, запрос помечается `llm_failed`, а затраченные токены всё равно считаются. Для ответов генератора то же самое: при неудаче ответ пустой и помечен `answer_failed`. Доля таких сбоев выводится в `evaluate` и сохраняется в `*.metrics.jsonl`. Если дневная квота исчерпана, прогон останавливается и продолжается позже той же командой.

Если команду запустить раньше, чем готовы её входные файлы (например, `tune` до `prepare`), она сообщит, какой шаг нужно сделать первым.

Без `--answers` выполняется только ранжирование. Генерацию можно добавить позднее, повторив ту же команду с `--answers`: готовые ранжирования сохранятся. `evaluate` без этого флага считает только поиск и расход реранжирования. Для отдельного режима вместо `all` указать его имя. Полному LLM и каскадам нужен завершённый BERT-прогон для выбранного split (это запасной порядок при сбое LLM), каскадам также сохранённые пороги.

Другой файл настроек:

```bash
rerank --config another.toml prepare
```

`prepare` фиксирует 100 validation- и 300 test-запросов с seed 42. В исходной разметке HotpotQA несколько вопросов указывают опорное предложение, которого нет в абзаце (в используемых ревизиях таких три). Они пропускаются, их id печатаются и записываются в `skipped_queries.json`. Выборка равномерно распределяется между существующими группами `(level, type)`. Исходные splits BEIR сохраняются: `validation` берётся из BEIR `dev`, а BEIR `test` соответствует открытой HotpotQA `validation`. В последней представлены hard-вопросы, поэтому там балансируется тип `bridge/comparison`. Ответы, сложности и предложения опорных фактов добавляются по id из [HotpotQA](https://huggingface.co/datasets/hotpotqa/hotpot_qa); qrels и корпус взяты из [BEIR](https://huggingface.co/datasets/BeIR/hotpotqa). Distractor-контексты служат только источником разметки опорных предложений; поиск идёт по полному корпусу BEIR.

Первый `retrieve` кодирует все 5,23 млн документов. Эмбеддинги сохраняются порциями, поиск точный по cosine similarity. Только кэш float32-эмбеддингов занимает около 16 ГБ; дополнительно скачиваются корпус и разметка. После прерывания готовые порции используются повторно. Top-20 сохраняется один раз для обоих splits, все режимы читают этот файл.

## Пороги и метрики

`tune` перебирает пороги только на validation. Для каждого порога берётся LLM-порядок у неуверенных запросов, BERT-порядок у остальных. Выбирается вариант с минимальным расходом токенов, у которого средний nDCG@10 отстаёт от полного LLM не более чем на `ndcg_tolerance` (по умолчанию 0,02 абсолютных пункта). Это параметр эксперимента, а не доказательство близости качества. Пороги сохраняются в `thresholds.json` и повторной командой не меняются; test при выборе порогов не читается.

Считаются nDCG@10, Recall@20, MRR@10, полнота опорных фактов в top-5, доля вызовов LLM и токены на запрос. При `--answers` добавляются EM, token-level F1 и отдельный расход генератора. EM/F1 следуют [официальной оценке HotpotQA](https://github.com/hotpotqa/hotpot/blob/master/hotpot_evaluate_v1.py), включая особое правило для yes/no/noanswer.

Опорный факт считается покрытым, если совпадает название документа и полное опорное предложение присутствует в фактически переданном генератору тексте после обрезки. Это полнота доступных свидетельств, а не оценка того, использовал ли их генератор.

Для разностей каждого режима с полным LLM и с BERT (если эти режимы выбраны) считаются парные bootstrap-интервалы 95% по запросам; в `{split}.bootstrap.csv` колонка `reference` говорит, с чем сравнение. По умолчанию 2000 повторов с фиксированным seed. Оценка выполняется только после завершения всех выбранных режимов на одной выборке.

## Файлы

По умолчанию результаты находятся в `runs/main/`:

- `validation.jsonl`, `test.jsonl`, `sample_counts.json`, `skipped_queries.json` — вопросы, ответы, qrels, опорные факты, состав выборки и пропущенные вопросы с битой разметкой;
- `candidates.jsonl` — общие top-20 с текстами и cosine similarity;
- `{split}.{method}.jsonl` — порядок документов, контекст, расход API и ответы;
- `validation.gap.csv`, `validation.cosine.csv`, `thresholds.json` — кривые выбора порога и зафиксированные значения;
- `{split}.metrics.jsonl`, `{split}.summary.csv`, `{split}.summary.json`, `{split}.bootstrap.csv` — метрики по вопросам, средние и интервалы разностей.

Прогоны пишутся по одному запросу. При повторном запуске готовые записи пропускаются; если ответ добавляется позднее, в JSONL появляется новая запись того же id, при чтении используется последняя.

### Работа на двух машинах

Лимиты Groq считаются на ключ, поэтому двое участников со своими бесплатными аккаунтами могут делить split пополам:

```bash
rerank run --split test --method llm --part 1/2 --allow-api   # машина 1, свой ключ
rerank run --split test --method llm --part 2/2 --allow-api   # машина 2, свой ключ
```

`--part i/n` берёт каждый n-й вопрос, начиная с i. Обе машины должны начинать с одинаковых файлов (`config.toml`, папка `run_dir` после `prepare`, `retrieve` и BERT).
Потом на одной машине:

```bash
rerank merge --from путь/к/второй/run_dir --api путь/ко/второй/data/api.jsonl
```

`merge` добавляет строки и ответы, которых здесь нет, копирует `thresholds.json` и `gate.json`, если их здесь нет, и дописывает кэш API.
Он отказывается работать, если настройки или вопросы различаются. Записи кэша хранят короткий хэш ключа (не сам ключ):
чужие записи используются как кэш, но не считаются в локальный лимит этого ключа.

Записи в `data/api.jsonl` и файлы результатов дописываются под блокировкой файла, поэтому дорогую модель и генератор (у них отдельные лимиты) можно запускать одновременно в двух терминалах на одной машине. На Windows блокировки нет, там запускать по очереди.

`data/api.jsonl` содержит исходные ответы API, фактические input/output/total tokens, время вызова и ключ кэша. В сравнении режимов учитывается расход сохранённого ответа для каждого режима: это расход такого отдельного прогона. Реальный суммарный расход выполненных API-вызовов хранится в `data/api.jsonl`; использование кэша не добавляет туда новых записей.

Локальный бюджет считается отдельно для каждой модели за последние 24 часа. Перед вызовом резервируется оценка входных токенов и максимальный выход; при нехватке бюджета команда останавливается. Между вызовами выдерживается пауза по RPM/TPM. Оценка входа использует `o200k_harmony` и запас на служебные токены; фактический расход берётся из API. Значения в конфигурации соответствуют опубликованным [бесплатным лимитам Groq](https://console.groq.com/docs/rate-limits), но их нужно сверить с лимитами своего аккаунта. Ошибка API останавливает прогон, готовые результаты сохраняются; после восстановления доступа запускается та же команда.

Использовать ключ бесплатного плана. Автоматического перехода на платный тариф в коде нет, но и определить тариф по ключу код не может: поэтому команды с обращением к API запускаются только с `--allow-api`. Если бесплатный доступ требует карту, по плану этот сервис не использовать. Денежная стоимость здесь не рассчитывается.

План эксперимента лежит в `PLAN.md`, дополнения к нему (контрольные сравнения, пошаговый пример, список работ для сравнения) в `PLAN_ADDITIONS.md`.

## Анализ по сохранённым результатам

Эти команды не обращаются к API и не требуют ключей. Нужны завершённые `validation.bert.jsonl`, `validation.llm.jsonl`,
`test.bert.jsonl`, `test.llm.jsonl` и соответствующие файлы вопросов. `thresholds.json` остаётся неизменным.

```bash
rerank gate
rerank controls --split test --repeats 1000
rerank resplit --repeats 100 --calibration-size 100
rerank run --split test --method cascade_gate
rerank evaluate --split test --method cascade_gate
pip install -e ".[plots]"
rerank report --split test
```

Gate обучается только на `validation`. Признаки: разрыв 1–2, разрыв 1–5, std top-10; список находится в `gate.FEATURES`.
Стандартизация и логистическая регрессия обучаются отдельно внутри каждой из пяти частей кросс-проверки.
AUC и порог вычисляются по отложенным предсказаниям, затем модель обучается на всей validation для применения к test.
Метка — прирост nDCG@10 строго больше `--min-gain` (по умолчанию 0). При менее 10 положительных или 5 отрицательных
метках печатается предупреждение с долей положительных, модель не обучается. Настройки, части, id вопросов и предсказания
сохраняются в `gate.json`; файл замораживается. При применении к validation используются отложенные предсказания.
Пересечение обучающих и тестовых id отклоняется. `cascade_gate --answers` использует только уже сохранённые ответы;
при их отсутствии останавливается. `all` включает gate, когда есть `gate.json`.

`controls/` содержит CSV и JSON: бюджеты 10/25/50/75/100%, монетку, оракул, матрицы 2×3, AUC и сравнение при зафиксированном
пороге. `{split}.cases.csv` содержит по строке на вопрос (вопрос, ответ, заголовки опорных документов, разрыв BERT, вероятность gate, nDCG BERT и LLM, решения правил, top-5 заголовков у BERT и LLM); сначала идут вопросы, где решение gap-правила потеряло качество. Это файл для ручного разбора ошибок. Каждый бюджет означает ровно `floor(n * budget)` вызовов, включая оракул; фактическая доля записывается отдельно.
При равных оценках используется исходный порядок вопросов. Монетка выбирает столько же вопросов без возвращения,
с фиксированным seed; p05–p95 описывают разброс случайного выбора, а не доверительный интервал. При единственном классе AUC
не определён и записывается пустым. Кривая gate добавляется после `rerank gate`.

`resplit` по умолчанию объединяет validation и test, использует `validation_size` для калибровки (при `--source validation` или `test` половину выборки), повторяет разбиение 100 раз.
Параметры `--source both|validation|test`, `--calibration-size`, `--repeats` позволяют изменить этот протокол.
На каждой калибровочной части выбирается порог по правилу `tune`; качество проверочной части при выборе не используется.
В `controls/resplits.json` сохраняются id обеих частей, медиана и p05–p95, доля нарушений допуска. Это пересекающиеся
разбиения, не независимые проверки. Смешивание исходных dev/test сохраняет различие распределений из `PLAN_ADDITIONS.md`.

`report` создаёт `report/{split}/figure_2.png`, `.pdf`, `table_1.csv`, `.tex`, `table_2.csv`, `.tex` и `report.json`
по [RESULTS_PLAN.md](RESULTS_PLAN.md), разделам 2–4. Нужны также dense-результаты. Если gate не обучен (`gate.json` нет), строки и кривая gate пропускаются, остальное строится. Блок `criterion` в таблице 2 и `success_criteria` в `report.json` проверяют критерий успеха из раздела 0 `RESULTS_PLAN.md`: потеря nDCG@10 относительно полного LLM не больше `ndcg_tolerance`, доля вызовов меньше 0,5, и 95%-интервал разности с монеткой при той же доле вызовов выше нуля. Рисунок 1 не создаётся.
Таблица 1 содержит интервалы query-bootstrap для nDCG и парных разностей с LLM; неизвестные EM/F1 и расход генератора
оставляются пустыми. Монетка и оракул используют долю зафиксированного gap-правила. Таблица 2 включает матрицы для gap/gate,
сохранённые повторные разбиения, AUC и сравнение gap и gate при равном числе вызовов (gap и gate в таблице 1 работают при своих зафиксированных порогах, поэтому доли вызовов у них разные). На рисунке закрашенными точками отмечены рабочие точки обоих правил при зафиксированных порогах. Для gate повторное обучение по разбиениям не выполняется, соответствующие клетки пустые.
Линии рисунка считаются для каждого 1% вызовов (маркеры стоят на бюджетах 10/25/50/75/100%); для монетки рисуется точное ожидание. Строки gap и gate пересчитываются из сохранённых `bert`/`llm`; если есть живой прогон `cascade_gap`, `report` сверяет его с пересчётом и предупреждает о расхождениях. Полосы вокруг бюджетных кривых не строятся из разброса одного зафиксированного порога. LaTeX экспортируется фрагментами таблиц.

На искусственных файлах использовать `--mock` (либо `mock_data = true` в конфигурации или `"mock": true` в вопросах).
CSV/JSON помечаются `MOCK`, подписи рисунка и LaTeX-таблиц содержат `МАКЕТ`/`MOCK`. Это проверка экспорта, не результаты статьи.
Тесты блокируют сетевые соединения, используют искусственные данные и поддельный клиент API.
Метка `MOCK` сохраняется также в результатах `cascade_gate` и обычного `evaluate`. В таблице 1 сбои реранкера и генератора
показаны отдельно. Если меняется `--min-gain`, у AUC gate меняется целевая метка; её определение записывается в таблице 2.

`rerank estimate` печатает оценку запросов, токенов и дней по суточным и минутным лимитам из конфигурации, не создавая прогон.
По умолчанию: validation + test для 120B, test × 3 способа (dense, bert, llm) для генератора, 2400 токенов на вызов 120B.
Каскады отправляют те же запросы, что `bert` и `llm`, и получают ответы из кэша, поэтому отдельно не считаются.
Если в `run_dir` уже есть сохранённые контексты (например, после `run --method bert`), размер запроса к генератору
измеряется по ним токенизатором `o200k_harmony` плюс 256 токенов на ответ; иначе берётся верхняя граница из лимитов
контекста и выхода. Источник оценки записывается в `answer_tokens_source`; её можно заменить `--answer-tokens 1000`.
Параметры `--queries`, `--answer-queries`, `--methods`, `--fraction`, `--rerank-tokens` задают другой объём.
Повторы не учтены, это планирование, не фактический расход. Полный LLM-контроль требует долю 1.0;
gate переиспользует сохранённые ответы и сам дополнительных вызовов не делает.

Опция `sample_source = "beir_test"` в новой конфигурации включает раздельные validation/test-выборки из одного BEIR `test`.
Обе выборки балансируются по доступным `(level, type)`, id не пересекаются; источник записывается в `sampling.json`.
Нужна новая пустая папка `run_dir`. По умолчанию опция выключена: остаются прежние BEIR dev/test.
Переход на этот протокол и размер validation нужно подтвердить перед реальными экспериментами.

`data/`, `runs/`, `.env` и `.venv/` исключены из Git.
