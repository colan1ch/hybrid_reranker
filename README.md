# Выборочное LLM-реранжирование

Обвязка для эксперимента на BEIR SciFact: один dense-поиск top-20, несколько вариантов ранжирования (таблица ниже). Вопрос здесь — научное утверждение (claim), нужный текст — абстракт статьи, которая его подтверждает или опровергает. Ответов нет, генератор не нужен.

| Режим | Ранжирование |
| --- | --- |
| `dense` | Порядок `BAAI/bge-base-en-v1.5` |
| `bert` | Все top-20 через `BAAI/bge-reranker-base` |
| `llm` | Все top-20 через GPT-OSS 120B |
| `cascade_gap` | BERT; при малом разрыве top-1/top-2 вызывается GPT-OSS 120B |
| `cascade_cosine` | Отдельный вариант: вызов LLM при низкой максимальной cosine similarity |
| `cascade_gate` | Логистический gate на трёх числах BERT; сборка по сохранённым результатам без API |

Реранкер BERT возвращает сырые logits, без sigmoid. LLM получает кандидатов в исходном dense-порядке; этот же вызов используется в полном LLM-режиме и каскадах. Для проверки, не занижает ли это полный LLM, есть `llm_input_order = "bert"`: кандидаты передаются в порядке BERT. Это другая настройка, поэтому нужна отдельная `run_dir`; туда можно скопировать `candidates.jsonl`, файл вопросов и BERT-результаты нужного split (при желании урезав файл вопросов до подвыборки), затем выполнить `run --method llm`.

Итоги прежнего этапа на HotpotQA: [docs/HOTPOTQA_SUMMARY.md](docs/HOTPOTQA_SUMMARY.md). Близкие работы: [docs/RELATED_WORK.md](docs/RELATED_WORK.md). Что рисуем и считаем: [RESULTS_PLAN.md](RESULTS_PLAN.md). Кто что делает: [WORK_PLAN.md](WORK_PLAN.md).

## Установка

Нужен Python 3.11 или новее.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev,plots]"
cp .env.example .env
```

В `.env` вписать `GROQ_API_KEY`. Он нужен только для LLM-реранжирования. Для подготовки данных, dense и BERT ключ не нужен.

Настройки находятся в `config.toml`. `device`, `batch_size` и `data_dir` можно менять в любой момент (например, `cuda` или `mps`): они не влияют на результаты, и запуск продолжается в той же папке `run_dir`. Любая другая настройка при изменении требует нового `run_dir`: настройки сохраняются рядом с результатами, смешивать результаты разных конфигураций команда не позволяет. Версии Python и библиотек сохраняются в `environment.json`.

**Не менять** в `config.toml` ничего, что входит в запрос к 120B (`rerank_instruction`, `rerank_doc_tokens`, `rerank_output_tokens`, `reasoning_effort`, `llm_reranker`, `candidate_count`, настройки поиска и BERT): ответы в кэше `data/api.jsonl` ищутся по точному запросу, и любое изменение заставит заново тратить лимит.

Тесты (без сети и без обращений к API): `pytest`.

## Данные

`rerank prepare` фиксирует выборки с seed 42. Оба набора берутся из 300 размеченных утверждений BEIR `test` и не пересекаются:

- **validation** — 50 утверждений: выбор порога и обучение gate;
- **test** — остальные 250 утверждений.

Утверждения перемешиваются с зафиксированным seed; первые `validation_size` идут в проверку, следующие `test_size` в тест. Проверка и тест из одного распределения, меньшая проверочная выборка является началом большей.
Проверочный набор нельзя взять из BEIR `train`: модели `bge` могли видеть эти утверждения при обучении (на проверочных из `train` дешёвые модели чуть сильнее, чем на `test`), и подбор порога на них получается слишком осторожным.

Корпус (5183 абстракта) и qrels берутся из [BEIR](https://huggingface.co/datasets/BeIR/scifact). `retrieve` кодирует корпус целиком и сохраняет top-20 один раз для обоих splits; на процессоре это порядка получаса. Все режимы читают этот файл. Если `candidates.jsonl` посчитан на другой машине, пользоваться нужно им: на CPU и GPU эмбеддинги чуть различаются, а общий `candidates.jsonl` нужен, чтобы запросы к 120B совпадали с кэшем.

## Запуск

```bash
rerank prepare
rerank retrieve

rerank run --split validation --method dense
rerank run --split validation --method bert
rerank run --split test --method dense
rerank run --split test --method bert

rerank run --split validation --method llm --allow-api   # 50 запросов
rerank tune
rerank gate

rerank run --split test --method llm --allow-api         # 250 запросов
rerank run --split test --method all --allow-api         # каскады берут ответы из кэша
rerank evaluate --split test --method all
```

Всё, что может обращаться к API (режимы `llm`, `cascade_*`, `all`), требует флага `--allow-api` (или переменной окружения `RERANK_ALLOW_API=1`). Флаг означает: «я проверил в консоли Groq, что аккаунт на бесплатном тарифе и к нему не привязана карта». Код сам тариф определить не может.
Флаг `--answers` для SciFact не используется.

Если LLM вернула неполный ответ или список, который не является перестановкой, запрос повторяется один раз с другими параметрами. Если и повтор не удался, берётся порядок BERT, запрос помечается `llm_failed`, а затраченные токены всё равно считаются. Если дневная квота исчерпана, прогон останавливается и продолжается позже той же командой.

Если команду запустить раньше, чем готовы её входные файлы (например, `tune` до `prepare`), она сообщит, какой шаг нужно сделать первым. Полному LLM и каскадам нужен завершённый BERT-прогон для выбранного split (это запасной порядок при сбое LLM), каскадам также сохранённые пороги.

Другой файл настроек: `rerank --config another.toml prepare`.

## Пороги и метрики

`tune` перебирает пороги только на validation. Для каждого порога берётся LLM-порядок у неуверенных запросов, BERT-порядок у остальных. Выбирается вариант с минимальным расходом токенов, у которого средний nDCG@10 отстаёт от полного LLM не более чем на `ndcg_tolerance` (по умолчанию 0,02 абсолютных пункта). Это параметр эксперимента, а не доказательство близости качества. Пороги сохраняются в `thresholds.json` и повторной командой не меняются; test при выборе порогов не читается.

Считаются nDCG@10, Recall@20, MRR@10, доля нужных абстрактов в top-5, доля вызовов LLM и токены на запрос.

Для разностей каждого режима с полным LLM и с BERT считаются парные bootstrap-интервалы 95% по запросам; в `{split}.bootstrap.csv` колонка `reference` говорит, с чем сравнение. По умолчанию 2000 повторов с фиксированным seed. Оценка выполняется только после завершения всех выбранных режимов на одной выборке.

## Файлы

По умолчанию результаты находятся в `runs/final/`:

- `validation.jsonl`, `test.jsonl`, `sample_counts.json`, `sampling.json` — вопросы, qrels и состав выборки;
- `candidates.jsonl` — общие top-20 с текстами и cosine similarity;
- `{split}.{method}.jsonl` — порядок документов, контекст и расход API;
- `validation.gap.csv`, `validation.cosine.csv`, `thresholds.json` — кривые выбора порога и зафиксированные значения;
- `{split}.metrics.jsonl`, `{split}.summary.csv`, `{split}.summary.json`, `{split}.bootstrap.csv` — метрики по вопросам, средние и интервалы разностей.

Прогоны пишутся по одному запросу. При повторном запуске готовые записи пропускаются.

### Запуск на всю ночь

Если суточный лимит или связь закончились, `rerank run` печатает `Paused ...` и завершается с кодом 75; на настоящую проблему (нет файла, неверные настройки) он завершается с кодом 0 и сообщением. Поэтому весь запуск можно поручить оболочке: она будет пробовать снова каждые 10 минут, пока всё не посчитано, и остановится сама.

```bash
caffeinate -i bash -c 'until rerank run --split test --method llm --part 2/2 --allow-api; do sleep 600; done'
```

Готовые вопросы пропускаются, повторные попытки при закрытом лимите ничего не стоят (запросов к API нет).

Собственная суточная защита считает скользящие 24 часа от первых запросов и может останавливаться раньше, чем реальный лимит Groq.
`RERANK_LOCAL_QUOTA=off` отдаёт решение серверу: если Groq отказывает (429 с долгим `retry-after`), запуск ставится на паузу так же, как раньше, и продолжается, как только Groq снова разрешит.

```bash
RERANK_LOCAL_QUOTA=off caffeinate -i bash -c 'until rerank run --split test --method llm --part 2/2 --allow-api; do sleep 600; done'
```

### Работа на двух машинах

Для общих прогонов с ключами нескольких участников сохрани их в `1.env`, `2.env`, `3.env` и так далее
(в каждом `GROQ_API_KEY=...`). Файлы подхватываются автоматически по порядку до первого отсутствующего номера.
Если нет `1.env`, используется обычный `.env`.
При желании список и порядок можно задать явно:

```bash
GROQ_ENV_FILES="1.env 2.env" rerank run --split test --method llm --allow-api
```

При ограничении квоты, ошибке доступа или соединения используется следующий ключ. Рабочий ключ остаётся активным,
расход считается отдельно для каждого участника. Если недоступны все, команда завершается с кодом 75:
её можно повторять тем же циклом с паузой.

Лимиты Groq считаются на ключ, поэтому двое участников со своими бесплатными аккаунтами могут делить split пополам:

```bash
rerank run --split test --method llm --part 1/2 --allow-api   # машина 1, свой ключ
rerank run --split test --method llm --part 2/2 --allow-api   # машина 2, свой ключ
```

`--part i/n` берёт каждый n-й вопрос, начиная с i. Обе машины должны начинать с одинаковых файлов (`config.toml`, папка `run_dir` после `prepare`, `retrieve` и BERT).
Потом на одной машине:

```bash
rerank merge --from путь/к/второй/run_dir --api путь/ко/второй/data/api.jsonl
```

`merge` добавляет строки, которых здесь нет, копирует `thresholds.json` и `gate.json`, если их здесь нет, и дописывает кэш API.
Он отказывается работать, если настройки или вопросы различаются. Записи кэша хранят короткий хэш ключа (не сам ключ):
чужие записи используются как кэш, но не считаются в локальный лимит этого ключа.

Записи в `data/api.jsonl` и файлы результатов дописываются под блокировкой файла. На Windows блокировки нет, там запускать по очереди.

`data/api.jsonl` содержит исходные ответы API, фактические input/output/total tokens, время вызова и ключ кэша. В сравнении режимов учитывается расход сохранённого ответа для каждого режима: это расход такого отдельного прогона. Использование кэша не добавляет новых записей.

Локальный бюджет считается отдельно для каждой модели за последние 24 часа. Перед вызовом резервируется оценка входных токенов и максимальный выход; при нехватке бюджета команда останавливается. Между вызовами выдерживается пауза по RPM/TPM. Значения в конфигурации соответствуют опубликованным [бесплатным лимитам Groq](https://console.groq.com/docs/rate-limits), но их нужно сверить с лимитами своего аккаунта. Ошибка API останавливает прогон, готовые результаты сохраняются; после восстановления доступа запускается та же команда.

Использовать ключ бесплатного плана. Автоматического перехода на платный тариф в коде нет, но и определить тариф по ключу код не может: поэтому команды с обращением к API запускаются только с `--allow-api`. Если бесплатный доступ требует карту, этот сервис не использовать.

## Анализ по сохранённым результатам

Эти команды не обращаются к API и не требуют ключей. Нужны завершённые `validation.bert.jsonl`, `validation.llm.jsonl`, `test.bert.jsonl`, `test.llm.jsonl` и соответствующие файлы вопросов. `thresholds.json` остаётся неизменным.

```bash
rerank gate
rerank controls --split test --repeats 1000
rerank resplit --repeats 100 --calibration-size 50
rerank run --split test --method cascade_gate
rerank evaluate --split test --method cascade_gate
rerank report --split test
```

Gate обучается только на `validation`. Признаки: разрыв 1–2, разрыв 1–5, std top-10; список находится в `gate.FEATURES`. Стандартизация и логистическая регрессия обучаются отдельно внутри каждой из пяти частей кросс-проверки. AUC и порог вычисляются по отложенным предсказаниям, затем модель обучается на всей validation для применения к test. Метка — прирост nDCG@10 строго больше `--min-gain` (по умолчанию 0). При менее 10 положительных или 5 отрицательных метках печатается предупреждение с долей положительных, модель не обучается. Настройки, части, id вопросов и предсказания сохраняются в `gate.json`; файл замораживается. Пересечение обучающих и тестовых id отклоняется. `all` включает gate, когда есть `gate.json`.

`controls/` содержит CSV и JSON: бюджеты 10/25/50/75/100%, монетку, оракул, матрицы 2×3, AUC и сравнение при зафиксированном пороге. `{split}.cases.csv` содержит по строке на вопрос (утверждение, заголовки правильных абстрактов, разрыв BERT, вероятность gate, nDCG BERT и LLM, решения правил, top-5 заголовков у BERT и LLM); сначала идут вопросы, где решение gap-правила потеряло качество. Это файл для ручного разбора ошибок. Каждый бюджет означает ровно `floor(n * budget)` вызовов, включая оракул; фактическая доля записывается отдельно. Монетка выбирает столько же вопросов без возвращения, с фиксированным seed; p05–p95 описывают разброс случайного выбора, а не доверительный интервал. При единственном классе AUC не определён и записывается пустым.

`resplit` по умолчанию объединяет validation и test, использует `validation_size` для калибровки, повторяет разбиение 100 раз. Параметры `--source both|validation|test`, `--calibration-size`, `--repeats` позволяют изменить этот протокол. На каждой калибровочной части выбирается порог по правилу `tune`; качество проверочной части при выборе не используется. В `controls/resplits.json` сохраняются id обеих частей, медиана и p05–p95, доля нарушений допуска. Это пересекающиеся разбиения, не независимые проверки.

`report` создаёт `report/{split}/figure_2.png`, `.pdf`, `table_1.csv`, `.tex`, `table_2.csv`, `.tex` и `report.json` по [RESULTS_PLAN.md](RESULTS_PLAN.md), разделам 2–4. Нужны также dense-результаты. Если gate не обучен (`gate.json` нет), строки и кривая gate пропускаются, остальное строится. Блок `criterion` в таблице 2 и `success_criteria` в `report.json` проверяют критерий успеха из раздела 0 `RESULTS_PLAN.md`: потеря nDCG@10 относительно полного LLM не больше `ndcg_tolerance`, доля вызовов меньше 0,5, и 95%-интервал разности с монеткой при той же доле вызовов выше нуля. Рисунок 1 не создаётся.
Таблица 1 содержит интервалы query-bootstrap для nDCG и парных разностей с LLM. Монетка и оракул используют долю зафиксированного gap-правила. Таблица 2 включает матрицы для gap/gate, сохранённые повторные разбиения, AUC и сравнение gap и gate при равном числе вызовов (gap и gate в таблице 1 работают при своих зафиксированных порогах, поэтому доли вызовов у них разные). На рисунке закрашенными точками отмечены рабочие точки обоих правил при зафиксированных порогах. Для gate повторное обучение по разбиениям не выполняется, соответствующие клетки пустые. Линии рисунка считаются для каждого 1% вызовов (маркеры стоят на бюджетах 10/25/50/75/100%); для монетки рисуется точное ожидание. Строки gap и gate пересчитываются из сохранённых `bert`/`llm`; если есть живой прогон `cascade_gap`, `report` сверяет его с пересчётом и предупреждает о расхождениях. LaTeX экспортируется фрагментами таблиц.

На искусственных файлах использовать `--mock` (либо `mock_data = true` в конфигурации или `"mock": true` в вопросах). CSV/JSON помечаются `MOCK`, подписи рисунка и LaTeX-таблиц содержат `МАКЕТ`/`MOCK`. Это проверка экспорта, не результаты статьи.

`rerank estimate --answer-queries 0 --rerank-tokens 4400` печатает оценку запросов, токенов и дней по суточным и минутным лимитам из конфигурации, не создавая прогон. Один запрос к 120B на SciFact стоит около 4,4 тысячи токенов (4097 на вход измерено плюс ответ), то есть около 45 запросов в сутки на ключ. Каскады отправляют те же запросы, что `bert` и `llm`, и получают ответы из кэша, поэтому отдельно не считаются. Параметры `--queries`, `--methods`, `--fraction` задают другой объём. Повторы не учтены, это планирование, не фактический расход.

`data/`, `runs/`, `.env`, `*.env` и `.venv/` исключены из Git.
